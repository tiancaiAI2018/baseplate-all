# 流程办理

自己的流程数据。所有工具都是只读的服务端查询，数据范围由服务端按角色和参与关系校验。

## 什么时候用

- 「我有哪些待办」「有什么要我审批的」→ `workflow_list_my_tasks`
- 「我发起了哪些流程」「我提交的单子」→ `workflow_list_my_started`
- 「我那单走到哪了」「现在卡在谁那里」→ `workflow_instance_progress`
- 「我审批过什么」「我上次怎么批的」→ `workflow_list_my_done`
- 「我还有多少事没处理」→ `workflow_my_summary`
- 「这单要填什么」「之前填了什么」→ `workflow_task_detail`

## 怎么做

1. **先定位再展开**。用户说「我发起的那单」时，先 `workflow_list_my_started` 拿到
   `instanceId`，再用 `workflow_instance_progress` 查进度；不要凭空构造 id。
2. **默认只看未走完的**。`workflow_list_my_started` 不传 state 就是 RUNNING；
   只有用户明确问「历史上」「全部」时才传 FINISHED / ALL。
3. **业务单号可以直接查**。用户嘴里说的是「报销单 BIZ-2026-001」，
   直接把它作为 `businessKey` 传给 `workflow_instance_progress`，不用先查列表。
   如果返回 `ambiguous=true`，说明匹配到多单，把候选列给用户选，**不要替他挑**。
4. **进度图由工具渲染**。`workflow_instance_progress` 返回的 `ui` 会让前端画一张
   带高亮的办理进度图（绿=已走过，橙=当前，红=被打回）。
   正文里不要再用文字或 ASCII 画流程图，也不要把返回的 JSON 抄一遍。
5. **数字类问题用汇总**。问「我还有多少事」用 `workflow_my_summary`，
   它会渲染成四个数字卡片；不需要再逐条拉列表。
6. **回答要短**。卡片已经把明细摆出来了，正文只补一句结论，
   例如「这单停在部门经理审批，已经走了 2 步」。

## 边界

- **不代替用户审批**。现在的工具里没有同意/驳回/打回能力，这是刻意的：
  审批必须由本人在办理抽屉里确认，审计日志要能对应到自然人。
  用户让你「帮我批了」时，说明原因并引导他点列表卡片或待办页的「办理」按钮。
- **不编造数据**。列表里没有的单号、没查到的实例，如实说没查到；
  查不到别人的单通常是数据范围限制，不要换 id 反复重试，也不要暗示是系统故障。
- **不猜节点名**。进度里的节点名来自历史任务轨迹，返回什么就用什么。
- **不把 `ui` 当业务数据**。`ui` 只是给前端的渲染指令，
  回答用户时用 `status`、`currentNodes`、`tasks` 这些字段。
