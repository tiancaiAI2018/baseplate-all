# ADR-0005 · Agent 全程接管编排 + 流式事件协议

- 状态：**已接受**（2026-09-30），决策人：用户
- 否决对象：本人在 `08-P0c 评审稿 v1` 中推荐的选项 C（双形态）
- 影响范围：`com.cuntong.ai` 全部、`t_ai_message` 字段、`/api/ai/**` 接口形态、降级链定义

## 决策

1. **选 A：agentscope 的 `ReActAgent` + `Toolkit` 全程接管编排**，不是只有 FALLBACK 兜底。
2. **流式输出**：像常见 AI 应用那样，把工具调用与各类状态串成进度，前端能看到「确实在干活」。
3. **向量检索先用全文检索替代**，接口留可替换点，后续切 pgvector。

## 我上一版判断错了一处，先认领

v1 里我说选 A 的致命问题之一是「路径不确定 → 评测集写不出断言」。
**在流式的前提下这条不成立**：工具调用会作为独立事件推给前端，
`tool_call` 序列本身就是可采集、可断言的执行路径。

结论：A 的可测性靠流式事件**补回来了**。所以 A 的真正代价只剩成本与延迟两项，
而这两项我有量化方案（见第 3、5 节），不是「说不清」。这是选 A 变得可行的关键。

## 选 A 后必须重新定义的三件事

### ① 「意图集封闭」→ 重新表述为「工具集封闭」

文档 1.3 把「意图集封闭」列为不可协商约束。A 形态下模型自由决定调用路径，
字面上的「封闭意图集」没了。但约束的**实质**可以保住：

> **Agent 可调用的工具是一份写死在代码里的白名单（10 个），不进 `t_config`、不可后台增删。**
> 新增工具要改代码 + 走评审。

这样「模型不可能到达设计之外的数据」仍然成立，只是边界从「9 个意图」变成「10 个工具」。
配套两条：
- **ArchUnit 断言**：`com.cuntong.ai.tool` 只能依赖 `biz.*.api`，不得出现任何数据访问类型。
- **工具描述精简**：`description` 写死，不允许运营改写——它决定模型能不能选对工具，
  改坏了等于整个 AI 失效，风险等级等同于系统提示词（文档 6.15 已把提示词定为只读）。

### ② 「降级链」→ 从「跳过某一段」改成「Agent 能力降级」

文档 6.14 的降级链是按「段」表达的（跳过意图判定、跳过生成段）。
A 形态下没有段，只有 Agent 循环。重新表述：

| 级 | 触发 | 返回 |
| --- | --- | --- |
| 0 | 正常 | 工具结果 + 卡片 + 引用 + 模型组织的正文 |
| 1 | 模型生成慢（流式已推完卡片） | **卡片与模板话术先到，正文后补或就不补** |
| 2 | Agent 规划失败（首轮决策超时/不可用） | 跳过 Agent，**改用规则层命中的意图直接跑对应 Tool + 模板拼装** |
| 3 | 闸门 / 熔断 | `degraded=true` + 工具结果直出 |
| 4 | 工具全失败 | 类目宫格 + 通讯录入口 |
| 5 | 全站不可用 | 本地应急号码页（bootstrap 缓存） |

**第 1 级在流式下变得很自然**，这是 A + 流式的真正好处：
卡片先到、正文可以慢，用户不会觉得卡住。**这一条要在设计里明确写出来并被利用**，
否则等于白拿了一个降级级次。

### ③ 总预算：3 秒 → 10 秒（**需要你确认**）

文档 6.1 的总预算是 3 秒。A 形态下 3 秒不够（Agent 首轮决策 + 1–3 轮工具 + 生成）。
建议：

| 场景 | 总预算 | 依据 |
| --- | --- | --- |
| 常规提问 | **10 秒**（首字目标 200ms，见下） | Agent 平均 2 轮工具 + 1 次生成 |
| `URGENT_HELP` | **800 ms，且不进 Agent** | 应急场景不能让模型规划 |

首字 200ms 是可以做到的：`step` 事件不依赖模型，进管道立刻发。
**「没卡住」的观感来自事件密度，不来自模型速度** —— 这是流式设计的要点。

## 代价（量化，不是「没关系」）

| 项 | v1（确定性管道） | A 形态 | 说明 |
| --- | --- | --- | --- |
| 单次输入 token | ~130（规则命中，零调用） | ~6000–9000 | 每次循环都要重发工具 schema + 累积历史 |
| 单次输出 token | ~200 | ~400 | |
| 调用次数 | 0–2 | 2–4 | 步数上限 4 |
| token 总量 | 1× | **约 3–5×** | |
| 折算月成本（单村） | ≈3.9 元（09-29 实测口径） | **≈12–20 元** | 已接近 20 元闸门 |

**这张表是估算，必须实测校准**（见 08 文档第 9 节）。
管控手段：步数上限 4、决策用 LITE 档、生成才用 STANDARD、工具结果做缓存（缓存检索不缓存答案）。

## 残留风险

1. **成本从「不是约束」变成「接近闸门」**。文档 1.3 的结论「模型费不是商业模式约束」
   是按确定性管道算的，A 形态下这个结论需要重新验证。
2. **延迟特征变了**。首字快但整体完成时间变长（10 秒级）。
   老人能不能接受 10 秒，**没有用户测试数据**。
3. **小程序 chunked 真机表现未验证**。`wx.request({enableChunked:true})` + `onChunkReceived`
   是官方支持的，但本项目**没有真机验证过**，也没有在弱网下验证过。
4. **工具选错是新的失效模式**。确定性管道下最坏是「命中错意图」，
   A 形态下多了「模型选了不相干的工具」——需要埋点统计工具选择正确率。

- [ ] 工具选择正确率埋点上线，作为独立指标看
