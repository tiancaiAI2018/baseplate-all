# 07 · 部署与运维

## 部署栈

Docker + Jenkins，**不引入 K8s**。村级规模用 Compose 完全够，
而且出问题时信息员拔电重启就能恢复。

## 形态 A（村级单机）

一台 4C8G，Compose 起：nginx / app / postgres / redis / minio / backup。
配置见仓库根目录 `docker-compose.yml`。

**一个坑先写在最前面**：postgres 镜像必须是 `pgvector/pgvector:pg16`。
官方 `postgres:16` 装不上 `vector` 扩展，Flyway V1 会直接失败。

## 启动前的自检

应用启动会校验（不对直接退出，不带着错误配置跑起来）：

| 项 | 校验 |
| --- | --- |
| `CT_CRYPTO_KEY` | 必须是合法 Base64 且解出 32 字节 |
| `CT_HASH_KEY` | 必须解出 ≥16 字节 |
| `CT_JWT_SECRET` | 长度 ≥32 字节 |
| `cuntong.ai.enabled=true` | 对应 provider 的 apiKey 必须非空 |

## 密钥（一律环境变量，不进代码库、不进镜像）

```
CT_CRYPTO_KEY   # 号码加密主密钥：openssl rand -base64 32
CT_HASH_KEY     # HMAC 盐
CT_JWT_SECRET   # JWT HS256，>=32 字节
CT_DB_URL / CT_DB_USER / CT_DB_PASSWORD
CT_REDIS_HOST / CT_REDIS_PORT
CT_OSS_ENDPOINT / ACCESS_KEY / SECRET_KEY
CT_WX_APPID / CT_WX_SECRET
DASHSCOPE_API_KEY / OPENAI_API_KEY / ANTHROPIC_API_KEY
```

完整清单见 `.env.example`。

## RLS 生效前提（否则第二道隔离是假的）

PG 对**表 owner 与 superuser 默认不施加 RLS**。生产必须：

```sql
CREATE ROLE cuntong_app LOGIN PASSWORD '...';
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO cuntong_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO cuntong_app;
-- 不要给 BYPASSRLS，也不要用建表账号跑应用

-- 审计日志：只给 INSERT + SELECT
REVOKE UPDATE, DELETE ON t_audit_log FROM cuntong_app;
```

## 定时任务

| 任务 | 频率 | 职责 |
| --- | --- | --- |
| `EventPoller` | 5 秒 | 消费 `t_event`，更新索引并清缓存 |
| `RecordingCleaner` | 每天 02:00 | 清理过期录音（7 天是设计承诺） |
| `ExpireArchiver` | 每天 03:00 | 公告/供需过期归档 |
| `IndexConsistencyChecker` | 每天 04:00 | 六项一致性检查，期望值恒为 0 |
| `GateResetJob` | 每天 00:05 | 重置各村日 token 计数 |

本轮只注册了 `EventPoller`（消费动作是空实现，等 P0-c 的索引写入）。
其余任务的骨架未建。

任务约定：每个必须幂等；多实例安全用 `FOR UPDATE SKIP LOCKED` 或 Redis 锁，
**不用「只在主节点跑」这种配置**——那是最容易被忘记的隐性依赖。

## 备份与恢复

| 数据 | 保留期 | 方式 |
| --- | --- | --- |
| 业务数据（PG） | 长期 | 每日 `pg_dump` + WAL 归档，保留 7 份滚动 |
| 审计日志 | ≥6 个月 | 随库备份 + **另存一份到异地对象存储**（防误删库把审计也删了） |
| 录音文件 | 7 天 | 不备份 |
| 公告图片 / 授权凭证 | 长期 | 对象存储开启版本化 |

**恢复演练**：每季度在测试环境做一次「从备份恢复到可用」并记录耗时。
没演练过的备份不算备份。

## 告警（必须带定位信息）

一条标准：告警文本里必须包含「**是哪个村、哪个意图/接口、什么原因、影响多少**」。
做不到这四点的告警，收到之后第一件事还是要登录服务器查日志——那就等于没告警。

| 告警 | 阈值 |
| --- | --- |
| 接口错误率上升 | >1% 持续 5 分钟 |
| AI 降级触发 | >5 次/小时（带降级原因） |
| 索引一致性检查 >0 | 任何一项 |
| 成本异常 | 日成本 > 近 7 日均值 3 倍 |
| 成本闸门触发 | 任意村（闸门触发本身就是事件，不是正常状态） |
| 越权访问 | 任何一次 40301 |
| 日志出现明文号码 | 任何一次（安全事件） |

## 日志规范

- JSON 结构化，字段固定：`ts level traceId uid villageId module action msg cost`
- **脱敏**：手机号、身份证、姓名在写入前替换。有一条 CI 断言扫日志模板。
- ERROR 只给「需要人处理」的。**不要把正常业务分支打成 ERROR**——
  零命中、降级、低置信度确认都是设计好的分支。
  打成 ERROR 会让运维对 ERROR 麻木，真故障就被淹没了。
- AI 日志额外记意图、置信度、是否降级、规则是否命中、token、耗时；
  **不记原文**（只记 hash 与长度）。

## 功能开关

`cuntong.feature.ai-enabled` 与 `voice-enabled`。
模型供应商挂了、成本异常、AI 回答出批量问题时，
30 秒就能止血，而不是紧急发版。
