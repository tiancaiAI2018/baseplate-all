## 真实 PG 上的验证（2026-09-30 晚，120.53.45.173:5433/cuntong）

用户提供了远程 PostgreSQL 16.14，首次在真实库上完成：

| 步骤 | 结果 |
| --- | --- |
| Flyway 迁移 V1~V6 | **成功**（7.96s，27 张 t_ 表就位；pg_trgm 装上，无 pgvector → V6 按设计跳过） |
| 种子数据 | 村 1 / 类目 6（带别名）/ 服务商 3 / 联系人 4 / 公告 3 |
| 端到端冒烟 9 条路径 | **全部 200**：登录、bootstrap、首页聚合、类目、服务商列表、**拨号（解密互通）**、问一句（规则命中+卡片）、发供需 INSERT、供需回读、公告列表 |

冒烟抓出并修掉一个纯单测抓不到的 bug：**PG 的 `RETURN_GENERATED_KEYS` 返回整行**，
`KeyHolder.getKey()` 直接炸 —— 四个写点（user/notice/provider/wall）全部改为显式 `new String[]{"id"}`。

Redis 缺失问题通过 `KeyValueStore` 接口 + 内存实现解决（`CT_REDIS_MOCK=true` 仅限本地，
生产必须真 Redis：refreshToken 重启即失等于没有登录态）。

## 期望值恒为 0 的一致性检查（P0-d 要实现）

这类检查最好运维——不需要调阈值，也不会误报。设计检查项时应优先找这类：

| # | 检查项 | 期望 |
| --- | --- | --- |
| 1 | 索引 chunk 数 vs 源表有效记录数 | 差值 ≤ 在途事件容差 |
| 2 | 已删除记忆但索引 chunk 仍有效 | **0** |
| 3 | 已撤回授权的服务商但仍在索引中 | **0** |
| 4 | 已撤回/已过期公告但仍在索引中 | **0** |
| 5 | chunk 的 `source_version` 落后于源表 | 0 或仅在途 |
| 6 | 索引文本中含 11 位手机号 | **0**（出现即为安全事件） |

## 性能目标（口径写清，避免验收时扯皮）

| 场景 | 目标 |
| --- | --- |
| 普通列表接口 | P95 < 300 ms |
| AI 提问（非流式） | P95 < 3 s（同时是熔断线） |
| AI 首字（流式） | < 1.2 s |
| 搜索接口 | P95 < 500 ms |
| 并发 | 20 QPS 无错误 |

压测场景要按「**一条公告发出去之后 200 个人同时点开**」设计，
而不是均匀 20 QPS——真实的高峰不是均匀流量。

## 怎么跑

```bash
# 单机完整验证（无 Docker 也能跑）
mvn -B clean test -Dmaven.repo.local=.mvn-repo

# 架构断言单独跑（CI 的第二阶段）
mvn -B test -Dtest=ArchitectureRulesTest -Dmaven.repo.local=.mvn-repo

# 静态检查（不破坏 compile，CI 单独一步并阻断）
mvn -B checkstyle:check -Dmaven.repo.local=.mvn-repo

# 集成测试（需要 Docker）
mvn -B verify -Dgroups=integration -Dmaven.repo.local=.mvn-repo
```

> `-Dmaven.repo.local=.mvn-repo` 是本机沙箱的临时约束（`~/.m2` 不可写），
> 环境恢复后可以去掉。
