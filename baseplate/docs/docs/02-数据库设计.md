# 02 · 数据库设计

27 张表：业务 12 + AI 8 + 系统 7。Flyway 脚本在 `src/main/resources/db/migration`。

## 迁移脚本

| 脚本 | 内容 |
| --- | --- |
| `V1__init_core.sql` | 扩展（`vector`、`pg_trgm`）+ t_village / t_user / t_user_role / t_admin_user / t_dict |
| `V2__content.sql` | t_notice / t_notice_read / t_service_category / t_provider / t_contact / t_wall_post / t_guide |

| `V6__pgvector_optional.sql` | **能力探测**：有 pgvector 才装扩展+embedding 列+HNSW；没有则跳过（fulltext 不受影响）。实测托管 PG 常不带 pgvector，硬装会让整个迁移链第一步就死 |

按**依赖顺序**拆，不是按章节顺序——这样每次部署都能单独验证一步。
已发布的脚本永不修改，要改就加新脚本。

## 建表规范（13 条，全表统一）

| 项 | 约定 |
| --- | --- |
| 主键 | `bigint GENERATED ALWAYS AS IDENTITY`。不用 UUID——单库单点，自增的索引效率与可读性都更好 |
| 审计四件套 | 所有表带 `created_at` / `updated_at` / `created_by` / `updated_by`（系统写入为 0） |
| 时间 | 一律 `timestamptz`，按 UTC 存，展示层转 GMT+8 |
| 逻辑删除 | `deleted_at timestamptz null`；唯一约束一律用**部分索引** `WHERE deleted_at IS NULL` |
| 多村隔离 | 业务表与 AI 表 `village_id bigint NOT NULL` 并建索引 |
| 枚举 | `smallint` + 代码枚举类 + `t_dict`。不用 PG 原生 enum——加值要改类型 |
| 布尔 | `boolean NOT NULL DEFAULT false` |
| 金额 | `numeric(10,2)`，不用浮点 |
| 文本 | 标题 `varchar(120)`、名称 `varchar(64)`、短说明 `varchar(500)`、**正文一律 `text`** |
| 手机号 | `phone_enc varchar(255)` + `phone_hash char(64)`。**明文列一个都没有** |
| JSON | `jsonb`，只用于不需要按内部字段查询的结构 |
| 注释 | 每张表每个字段都有 `COMMENT ON`，写业务含义而不是重复字段名 |

## 索引与典型查询

| 场景 | 索引 |
| --- | --- |
| 公告列表 | `(village_id, status, expire_at)` |
| 公告分类 | `(village_id, category, publish_at DESC)` |
| 公告关键词 | `GIN (content_text gin_trgm_ops)` |
| 服务商 | `(village_id, category_id, status, accept_status, verify_status)` |
| 服务商查重 | `UNIQUE (village_id, phone_hash) WHERE deleted_at IS NULL` |
| 向量检索 | `HNSW (embedding vector_cosine_ops)` |

两条纪律：
1. 列表查询的排序字段必须进索引，否则数据一多就会出现「偶发慢查询」——这类问题最难查。
2. 「接单中优先」用 `(accept_status = 1) DESC` 写在 SQL 里，**不在应用层排**——应用层排序会破坏分页。

## 多村隔离（三道）

1. **每表带 `village_id`**：即便第一版只服务一个村也做进去，事后补要改所有表和所有查询。
2. **应用层自动注入**：`DataScope` 从 JWT 取 villageId，**不接受请求参数传**——
   那等于任何村都能访问别的村。`SqlVillageIdScanTest` 会扫每个 SQL 字符串。
3. **RLS（第二道保险）**：核心五表（t_user / t_notice / t_provider / t_contact / t_ai_memory）启用行级安全。

### RLS 生效的前提（否则这道保险是假的）

PG 对 **表 owner 与 superuser 默认不施加 RLS**。所以应用连接账号必须：

```sql
CREATE ROLE cuntong_app LOGIN PASSWORD '...';
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO cuntong_app;
-- 注意：不要用建表的那个账号跑应用，也不要给 BYPASSRLS
```

跨村角色（乡镇 / 县级）的 `app.village_id` 不设置，策略放行全表，
但响应里必须带 `villageName`——不标明是哪个村，几乎一定会看错。

## 号码字段

| 环节 | 处理 |
| --- | --- |
| 录入 | 本人填写 + 短信校验；后台代录必须上传凭证，否则 Service 拒绝保存 |
| 存储 | `phone_enc`（AES-256-GCM，每条独立 IV，格式 `v1:` + Base64(IV‖密文‖Tag)）+ `phone_hash`（HMAC-SHA256） |
| 检索 | **号码不参与检索**，查重靠 hash。不支持模糊/前缀/范围查询（加密后做不到，本项目也不需要） |
| 入索引 | `chunk_text` 不含号码，入库前有正则扫描，命中 11 位手机号拒绝入库并告警 |
| 展示 | 一律 `Masker.phone()` → `138****2210`。**不提供复制号码**，只有拨打电话 |
| 拨号 | `/dial` 返回完整号，写审计，前端交给系统拨号组件，不渲染成文本 |
| 撤回 | 联动置失效索引 chunk + 清答案缓存 |

### 关于「脱敏展示不写审计」

`PhoneService.mask()` 会解密一次再脱敏，**不写审计**。
这与设计文档 7.1「只要解密就留痕」的字面要求不同，理由：

- 审计真正要盯的是「明文离开服务端」——拨号（明文返回客户端）与后台查看（明文进入人眼）。
- 脱敏展示解密后立刻被处理成 `138****2210`，明文不出这个方法、不进日志、不进缓存。
- 如果这里也写审计，一次列表查询会写几十条 `PHONE_DIAL`，
  真正值得看的「谁拨了这个号」反而被淹没——那才是把审计做废了。

三个解密方法都在 `PhoneDecryptor` 里，`PhoneService` 是唯一门面，
ArchUnit 规则 7 保证没有第二条路径。
