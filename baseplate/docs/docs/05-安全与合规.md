# 05 · 安全与合规

## 认证与授权

| 层 | 实现 |
| --- | --- |
| 小程序 | 微信 `code2session` → 查/建用户 → 签发 JWT。**不索取手机号** |
| 后台 | 手机号 + 密码，BCrypt(cost=10) |
| token | accessToken 2 小时；refreshToken 30 天且**一次性使用**（Redis 存一份，换完即删） |
| 登录失败 | **不区分「账号不存在」与「密码错误」**——区分了等于帮攻击者枚举账号。连续 5 次锁 15 分钟 |
| 功能权限 | `@RequireRole` 注解，拦截器在进入 Controller 前校验 |
| 数据权限 | `DataScope` 从 JWT 取 villageId，**不接受请求参数传 villageId** |
| 越权 | 命中 403 时写 `ACCESS_DENIED` 审计。越权尝试是重要信号，不能只返回一个 403 |

### 为什么 refreshToken 存在 Redis 而不是做成无状态 JWT

一次性使用必须有个地方把它作废，而无状态 JWT 没有作废机制。
这 30 天的 Redis key 换来的是「令牌被偷了能被踢掉」这个能力，值得。

## 号码明文的「三道门」

1. **本人授权同意**：服务商 `consent_status=1`；通讯录 `visible_scope` 命中。
   不满足则**连脱敏号都不返回**（返回脱敏号等于承认这个人有号）。
2. **调用方有明文权限**：只有 `can_view_phone_plain=true` 的后台账号能调明文接口。
   小程序端永远拿不到明文。
3. **留痕**：任何解密调用都写审计。

### 权限判定为什么不看 token 里的字段

`AdminServiceImpl.viewPhonePlain()` 会**回库再查一次** `can_view_phone_plain`。
令牌里的权限值是签发那一刻的快照，拿它做判等于相信一张旧照片——
权限随时可能被改掉。

## 审计日志

| 必审操作 | action_code |
| --- | --- |
| 查看号码明文 | `PHONE_VIEW_PLAIN` |
| 导出数据 | `DATA_EXPORT` |
| 修改权限与闸门 | `PERM_CHANGE` |
| 其他 | `NOTICE_RETRACT` / `PROVIDER_DISABLE` / `CONSENT_REVOKE` / `MEMORY_DELETE` / `ACCESS_DENIED` / `PHONE_DIAL` |

三条实现约束：

1. **只允许 INSERT**。数据库层只给应用账号 `INSERT, SELECT`，不给 UPDATE/DELETE。
   代码层也先自我约束一道：`AuditLogRepository` 里没有 UPDATE、没有 DELETE，
   `AuditService` 接口也没有任何修改方法。
2. 不允许改历史，没有物理删除入口。
3. **能按号码反查**：`queryByPhoneHash()` 入参是 hash 而不是明文——
   这样才能在不接触明文的前提下回答「谁看过我的号码」。

写入方式：注解 + AOP，不是业务代码里手写 `record()`。
手写会漏，尤其是异常分支——而恰恰是失败的操作最需要留痕。

## 四类授权（都在 `t_consent`）

| 类型 | 凭证要求 | 撤回后 |
| --- | --- | --- |
| 号码展示 | 本人勾选无需凭证；**代录必须上传凭证** | 索引 chunk 失效 + 清缓存，列表与 AI 都不再返回 |
| 代管家人 | 被代管人自己同意 | 代管人立即失去访问 |
| 位置（到组） | 无 | 清位置用途标记 |
| 个性化记忆 | 无 | 不再写入新记忆，已有记忆保留至用户主动删除 |

条款改版后**旧同意不自动延续**，需重新获取。

> 没有凭证的「已授权」等于伪造同意——Service 层硬校验拒绝保存。

## 默认收紧

两个默认值是刻意选的，请不要为了「方便」改掉：

- `t_contact.visible_scope` 默认 **4（不可查）**。
  数据保护类功能只有一种正确取向：默认收紧、要主动放开。
  反过来（默认开放、要主动收紧）在现实里一定出事，因为录入的人不会主动去收紧。
- `t_admin_user.can_view_phone_plain` 默认 **false**。

## 删除权（最容易被做错的一条）

界面上删成功 ≠ 真的删掉了。三个入口各自的清理清单：

| 入口 | 要清什么 |
| --- | --- |
| 删一条记忆 | ① 物理删除 ② 派生的索引 chunk 置失效 ③ 清该用户答案缓存 ④ 清 Redis 里引用该记忆的 L1 摘要 |
| 撤回号码授权 | ① `consent_status=2` ② 索引 chunk 失效 ③ 清 `SERVICE_SEARCH` 答案缓存 ④ 写审计 |
| 注销账号 | ① 档案与记忆物理删除 ② 全部索引 chunk 失效 ③ 会话原文清空 ④ `t_consent` 保留但去标识化 ⑤ 若其为服务商，执行撤回流程 |

**必须有一个一致性检查任务兜底**：这三条链路都是多步操作，
任何一步失败都可能留下孤儿数据。期望值恒为 0 的检查（见 06 章）每天跑，大于 0 就报。

## 模型侧边界

- 送进模型的文本在组装阶段就把手机号、身份证替换成占位符（`[PHONE_1]`），返回后再还原。
  这样即便厂商侧留了日志，也不含明文个人信息。
- **不进上下文的清单**：通讯录整表 · 任何号码明文 · 身份证/银行卡/健康信息 · 他人隐私记录 · 精确坐标。
- 本地日志同样脱敏：AI 请求/响应默认只记 hash 与长度。
- 境外端点：见 `adr/ADR-0003`。默认关闭，开启需要显式确认。

## 限流

| 维度 | 阈值 | 超限行为 |
| --- | --- | --- |
| AI 提问 | 单用户 30 次/小时、200 次/天 | **降级到关键词搜索形态**，不是报错 |
| 供需发布 | 单用户 5 条/天 | 42902「今天发得有点多，明天再发」 |
| 号码拨打 | 单用户 60 次/天 | 降级为脱敏展示 + 告警 |
| 登录 | 失败 5 次/15 分钟 | 锁定并告警 |
| 导出 | 3 次/天/账号 | 拒绝并写审计 |

**正常用户偶然触发要降级而不是报错**——老人看到红色错误页会以为坏了。
只有明显的机器行为（同 IP 多账号、固定间隔、无 UI 交互路径）才返回 429。
